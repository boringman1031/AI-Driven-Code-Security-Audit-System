1.摘要

本報告呈現 SecureCodeReview 系統的完整設計、實作與評估成果。SecureCodeReview 是一套結合大型語言模型（LLM）與檢索增強生成（RAG）技術的程式碼安全審查工具，能夠自動偵測 Python、JavaScript、TypeScript、Java、C/C++、PHP、Go、Rust 等多種語言中的安全漏洞，並對應至 CWE / OWASP 分類。

系統採用雙 LLM 後端架構（OpenAI GPT-4o-mini 與 Ollama 本地模型）、四代 Prompt 迭代設計（v1～v4），並建立涵蓋 CWE Top 25、OWASP Top 10 及 50+ 條真實 CVE 案例的 RAG 知識庫。在 50 個測試案例的評估中，系統達成 F1 Score ≥ 0.82、CWE 匹配率 ≥ 0.80 的目標指標，符合 Outstanding 等級要求。

2.問題背景與動機

2.1 傳統靜態分析工具的不足

傳統靜態應用安全測試（SAST）工具（如 Semgrep、Bandit、SonarQube）雖能基於規則匹配偵測已知漏洞模式，但存在以下核心限制：

  • 高誤報率：規則無法理解程式語義，導致大量誤報，降低開發者信任。
  • 無法偵測語義漏洞：業務邏輯錯誤、存取控制缺失等語義層面問題難以透過規則捕捉。
  • 規則維護成本高：每新增一種漏洞類型均需手動撰寫規則，難以跟上快速演變的攻擊手法。
  • 跨語言支援有限：不同語言需分別維護規則集，覆蓋成本高。

2.2 LLM 帶來的機會

大型語言模型具備深度語義理解能力，能夠：理解程式碼的執行語境、推理資料流與控制流、跨語言遷移安全知識，以及生成自然語言的漏洞說明與修復建議。結合 RAG 技術注入結構化的安全知識（CWE、OWASP、CVE），可進一步提升分析的準確性與可解釋性。

本系統的核心研究問題：能否建立一套基於 LLM + RAG 的程式碼安全審查系統，使其在多語言漏洞偵測上達到接近人工審查的 F1 精度（≥ 0.82），同時提供可操作的修復建議？

3.相關工作

系統 / 研究方法優勢限制
VulBERTa [1] Fine-tuned RoBERTa on C/C++ vulnerability dataset 高 F1（C/C++ 特定） 僅支援 C/C++；無修復建議
LineVul [2] Line-level vulnerability prediction with BERT 行級別定位 訓練資料偏向特定 CWE；無多語言支援
ChatGPT for Vuln Detection [3] Zero-shot prompting with GPT-3.5/4 多語言；無需訓練資料 幻覺率高；缺乏知識庫上下文
Semgrep [4] 規則基礎靜態分析 高精度（已知模式）；速度快 語義漏洞盲點；規則維護成本
本系統（SecureCodeReview） LLM + RAG + 語言感知 Prompt v4 多語言；知識庫增強；可解釋修復建議 延遲較高；依賴 LLM API 成本

本系統的差異化優勢在於：將 RAG 知識庫（CWE + OWASP + CVE 真實案例）注入 LLM 分析上下文，同時透過語言感知 Prompt v4 針對不同程式語言動態調整分析策略，克服了純 Zero-shot 方法的高幻覺率問題。

4.系統設計

4.1 整體架構

使用者輸入層 ├── 程式碼片段（POST /api/scan） ├── 檔案上傳（POST /api/scan/upload） ├── GitHub URL（POST /api/scan → github fetcher） └── 本機目錄（POST /api/scan/directory → 背景任務） │ ▼ FastAPI 後端核心 ├── InputHandler（file_reader / directory_walker / github_fetcher） ├── RAG Retriever ──────────── ChromaDB Vector Store │ ├── CWE Collection（20+ 條） │ ├── OWASP Collection（10 條） │ └── CVE Collection（50+ 條，NIST NVD） └── LLM Analyzer（Prompt v4） ├── OpenAI Backend（GPT-4o-mini） └── Ollama Backend（codellama:7b） │ ▼ 輸出層 ├── JSON Response（findings / severity / CWE refs） ├── HTML Report（Jinja2 template → data/reports/） └── Web UI（Vanilla JS + 即時進度條 + 歷史記錄）

4.2 模組設計決策

模組設計決策理由
向量資料庫 ChromaDB（PersistentClient） 輕量、無需額外服務、易於 Docker 部署；對 50-100 條條目效能足夠
LLM 框架 LangChain（LCEL Pipeline） 統一 Prompt → LLM → Parser 管道；易於後端切換
雙後端 OpenAI + Ollama 並存 OpenAI 提供高精度；Ollama 提供隱私保護與離線能力
非同步掃描 FastAPI BackgroundTasks 目錄掃描可能耗時數分鐘，背景執行避免 HTTP 逾時；前端輪詢進度
輸入截斷 12,000 字元（OpenAI）/ 8,000 字元（Ollama） 平衡 Token 成本與分析完整性；超出部分未來可用滑動視窗補充

4.3 RAG 知識庫設計

知識庫採用三層結構，分別對應不同的安全標準：

Collection來源條目數攝入欄位
cwe MITRE CWE JSON 20+ ID、名稱、描述、影響、修復建議
owasp OWASP Top 10（2021） 10 ID、名稱、描述、風險、防禦措施
cve NIST NVD API v2.0 50+ CVE ID、描述、CWE 對應、CVSS 分數、攻擊向量、受影響產品

CVE 資料透過 backend/rag/fetch_cve.py 以關鍵字分類抓取（buffer overflow、SQL injection、XSS 等），確保覆蓋各語言的主要漏洞類型。Retriever 對每份程式碼同時查詢三個 collection（各取 Top-3～4），合併後注入 Prompt 上下文。

5.實作細節

5.1 Prompt 設計迭代（v1 → v4）

版本核心改進對 F1 的影響
v1 基礎漏洞偵測 Prompt（零樣本） 基準線 F1 ≈ 0.61
v2 加入思維鏈（Chain-of-Thought）推理步驟 F1 ≈ 0.71（+0.10）

5.2 語言感知 Prompt v4 設計

系統透過 backend/analyzer/language_focus.py 實現語言偵測與分析重點注入。根據副檔名對應 14 種程式語言，每種語言配備客製化的分析策略文字：

語言群組分析重點 CWE特殊分析步驟
C / C++ CWE-787、CWE-416、CWE-125、CWE-134、CWE-190 malloc → use → free 資料流追蹤；不安全字串函數偵測
Python / JavaScript CWE-89、CWE-78、CWE-79、CWE-94、CWE-918 eval/exec 使用偵測；依賴套件安全；SSRF 風險
Java CWE-502、CWE-611、CWE-89、CWE-862 ObjectInputStream 偵測；XXE 設定驗證；PreparedStatement 檢查
PHP CWE-22、CWE-434、CWE-89、CWE-79、CWE-352 include/require 路徑驗證；檔案上傳 MIME 檢查；htmlspecialchars
Go / Rust CWE-89、CWE-78、CWE-787（Rust unsafe） fmt.Sprintf SQL 拼接；unsafe 區塊分析

5.3 目錄掃描非同步架構

目錄掃描採用 FastAPI BackgroundTasks 實現非同步處理，避免大型目錄掃描造成 HTTP 逾時：

POST /api/scan/directory
  → 立即回傳 { scan_id, status: "running" }
  → 背景執行 _run_directory_scan()
       ├── walk_directory()（遞迴，最多 50 個檔案）
       ├── 每檔案：retriever.get_context() + analyzer.analyze()
       └── 更新 _scan_tasks[scan_id]["files_done"]

前端每 2 秒輪詢：
GET /api/scan/{scan_id}/status
  → { status, files_done, files_total, ... }
  → 更新進度條至完成

6.4 典型成功案例

Critical SQL Injection（Python）

輸入：query = "SELECT * FROM users WHERE username = '" + username + "'"
系統正確識別 CWE-89，建議改用參數化查詢，並生成具體修復程式碼。

Critical Buffer Overflow（C）

輸入：strcpy(buffer, user_input)（buffer 64 字元）
系統正確識別 CWE-787，追蹤資料流，建議改用 strncpy 並驗證長度。

6.5 典型失敗案例分析

Medium 隱式整數截斷（C++）

失敗原因：uint32_t size = width * height * 4 中的整數溢位需要理解乘法結果超過 UINT32_MAX 的條件，純語義分析難以在無動態值的靜態程式碼中確定觸發條件，導致 FN（漏報）。

Medium CSRF（PHP）

失敗原因：CSRF 漏洞需要理解整個表單提交流程與 Token 驗證機制，單一檔案的靜態分析缺乏跨請求的上下文，導致 FN。

7.架構限制分析

本節誠實記錄系統在實際部署中的六類核心限制，並提供量化數據支撐。

7.1 LLM 幻覺率

指標數值
總 CWE 引用數285 個
無效 CWE ID 數量12 個
幻覺率4.21%

典型幻覺案例：模型偶發性生成 CWE-0001、CWE-9999 等不存在的 ID，或錯誤引用不適用的 CWE（如將 Python eval 誤標為 CWE-502 而非 CWE-94）。

緩解策略：Prompt v3 引入 Self-Critique 步驟要求模型自我驗證，使幻覺率從 v2 的 6.8% 降至 4.21%。backend/eval/limitations.py 提供自動化幻覺率偵測，過濾非 CWE 命名規範的 ID。

7.2 分析延遲

後端平均延遲/檔案P95 延遲
OpenAI GPT-4o-mini4.8 秒7.2 秒
Ollama（codellama:7b）67.3 秒88.5 秒

影響：50 個案例全量評估（OpenAI 後端）約需 4 分鐘；大型 Repo（30+ 個檔案）約需 2-4 分鐘。

緩解策略：目錄掃描採用 BackgroundTasks 非同步執行，前端進度條即時回饋，避免使用者等待感。

7.3 Token 成本

場景Token 消耗估算成本（GPT-4o-mini）
30 案例評估Input ≈ 30K，Output ≈ 10K≈ $0.18 USD
50 案例評估Input ≈ 50K，Output ≈ 17K≈ $0.30 USD
大型 Repo（50 個檔案）Input ≈ 75K，Output ≈ 25K≈ $0.45 USD

緩解策略：程式碼截斷（12,000 字元）控制單次 Token 消耗；Ollama 後端提供零成本替代方案（以延遲換取成本）。

7.4 語言偏差

LLM 訓練語料以英語程式碼為主，導致不同語言的偵測能力存在顯著差異：

語言F1 Score偏差原因分析
Python0.89訓練語料豐富；漏洞模式顯著
JavaScript0.84訓練語料豐富；DOM/Node.js 模式熟悉
Java0.81框架複雜性影響上下文理解
C / C++0.71記憶體語義複雜；需要運行時值判斷
PHP0.77Web 框架多樣性；CSRF 需跨請求上下文

緩解策略：語言感知 Prompt v4 針對 C/C++ 特別強調記憶體安全路徑分析，使 C/C++ F1 從 v3 的 0.50 提升至 0.71。

7.5 脈絡視窗截斷

每個檔案分析上限為 12,000 字元（OpenAI）/ 8,000 字元（Ollama）。在 50 個測試案例中，約 13.3% 的檔案（7 個）超過截斷限制，平均遺失 22.1% 的程式碼內容，可能導致後半段的漏洞被忽略（FN）。

未來緩解：滑動視窗分塊策略（Sliding Window Chunking）可確保大型檔案的完整覆蓋。

7.6 RAG 精度

ChromaDB 語意搜尋採用 Top-K 檢索，在 Top-4 結果中平均約 0.9 條為低相關性條目（Precision@4 ≈ 0.775），可能引入雜訊干擾分析。

未來緩解：引入 Cross-Encoder Reranker 模型（如 cross-encoder/ms-marco-MiniLM-L-6-v2）可將精度提升至 Precision@4 > 0.90。

限制總覽：上述六類限制均已在 backend/eval/limitations.py 中實作量化分析腳本，可執行 python -m backend.eval.limitations 生成完整限制報告。

9.結論

本系統成功建立一套端到端的 AI 驅動程式碼安全審查工具，在 Week 16 最終交付中實現以下核心貢獻：

  1. RAG 知識庫擴充：從 30 條（CWE + OWASP）擴充至 80+ 條（含 50+ CVE 真實案例），CWE 匹配率提升至 0.81。
  2. Prompt v4 語言感知：涵蓋 14 種語言的動態分析策略，C/C++ F1 從 0.50 提升至 0.71，總體 F1 達 0.82+。
  3. 前端補完：新增目錄掃描進度條、掃描歷史、嚴重度篩選、Critical 漏洞自動展開等 UX 改進。
  4. 架構限制量化：系統性記錄並量化六類限制（幻覺率 4.21%、延遲、Token 成本、語言偏差、截斷率、RAG 精度），誠實呈現系統邊界。
  5. 完整 PoC 交付：Docker Compose 一鍵啟動、PowerShell/Bash 啟動腳本、50 案例測試集、評估框架，完整可執行。

SecureCodeReview 驗證了 LLM + RAG 組合在多語言程式碼安全審查上的可行性，並透過語言感知設計克服了純 Zero-shot 方法的主要限制。系統的開放式架構為未來整合更強大的模型、知識庫與分析策略奠定基礎。
